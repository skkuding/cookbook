### 워터폴(Waterfall) vs 애자일(Agile) 

워터폴 방법론은 폭포수 방법론이라고도 불리며 이름에서도 알 수 있듯, 폭포처럼 위에서부터 아래로 순차적 개발을 진행하는 방법이에요!

요구사항 정의(설계) → 디자인 → 개발 → 테스트 → 배포의 과정이 순차적으로 진행돼요. 한단계씩 진행함에 따라 다시 이전 단계로 가지 않고 계속 진행하기에 다음 단계로 가기전에 완벽하게 요구사항을 반영하여 개발했다는 것을 전제로 합니다.

워터폴 방법론은 애자일 방법론이 등장하기 전까지 소프트웨어 개발 뿐 아니라 자동차, 선박 등 산업 현장에서 보편적으로 사용되던 프레임워크예요.

<img src="https://i0.wp.com/blogcodestates.com/wp-content/uploads/2023/03/%EC%9B%8C%ED%84%B0%ED%8F%B4-%EB%B0%A9%EB%B2%95%EB%A1%A0-%ED%8F%AD%ED%8F%AC%EC%88%98-%EB%B0%A9%EB%B2%95%EB%A1%A0-%EC%A0%95%EC%9D%98-%ED%94%84%EB%A1%9C%EC%84%B8%EC%8A%A4.jpg?resize=1024%2C544&ssl=1" width="720"/>

하지만 워터폴 방법론은 개발 도중 수정사항이 생길 경우 첫 단계부터 다시 수정해야 한다는 단점이 있어요. 그래서 생겨난 것이 바로 애자일 방법론이랍니다!

애자일(Agile)은 ‘기민한, 민첩한’이라는 뜻을 가지고 있어요. 따라서 애자일 방법론은 일정한 주기를 가지고 빠르게 제품을 출시하여 고객의 요구사항, 변화된 환경에 맞게 요구를 더 하고 수정해나가는 탄력적인 방법론을 말합니다.

짧은 사이클로 제품을 개발하고 테스트하고 피드백을 받아 보완하는 방식을 사용해요. 변화에 수동적으로 대처하기보다 변화를 하나의 고정값으로 전제하여 1~4주 작은 스프린트 단위로 디자인 → 개발 → 테스트를 진행합니다.

<img src="https://i0.wp.com/blogcodestates.com/wp-content/uploads/2023/03/%EC%95%A0%EC%9E%90%EC%9D%BC-%EB%B0%A9%EB%B2%95%EB%A1%A0-%EC%A0%95%EC%9D%98-%EC%9E%A5%EC%A0%90-%EB%8B%A8%EC%A0%90-%ED%94%84%EB%A1%9C%EC%84%B8%EC%8A%A4.jpg?resize=1024%2C562&ssl=1" width="720"/>

워터폴과 애자일은 생겨난 시기와 적합한 조직이 다를 뿐 둘 중 정답은 없어요! 팀마다 처한 상황이 다르기 때문에 우리 팀에 적합한 방법을 고민하여 적용하는 것이 중요합니다🔑

### 스쿼드에선 무슨 일을 하나요?
우선 스쿼드란 <b>하나의 목표를 달성하기 위해 모인 작은 프로젝트 팀</b>이에요. 보통 개발 조직에서 스쿼드는 기획자, 디자이너, 프론트엔드, 백엔드 등 여러 역할의 사람들이 함께 모여서 특정 기능이나 서비스 영역을 책임지는 단위를 말합니다.

[스쿼드란?](https://oliveyoung.tech/2025-07-30/squad-description/) 👉 스쿼드 개념이 어렵다면 읽어보아요!

현재 스꾸딩은 두 가지 스쿼드로 나뉘어 코드당 서비스를 개선하는 작업을 하고 있어요.  
(Course 기능 중심의 \_\_init\_\_, Contest 기능 중심의 유자차로 나뉘어져 있답니다!)

기획팀은 사용자의 문제를 발견하고, 해결 방향을 정하고, 디자인/개발 팀이 실제로 구현할 수 있게 정리하는 역할을 해요.

지금까지 배운 내용들을 활용해 다음과 같은 일을 하게 됩니다!

1. 문제 정의하기
    - 사용자나 서비스에 어떤 문제가 있는지 찾아요.
    - 해결해야 할 문제, Pain Point를 정리해주면 좋아요!
2. 사용자 이해하기
    - 개발자 입장이 아닌, 실제 유저들의 입장을 파악해요.
3. 기능 기획하기
    - 문제를 해결하기 위해 어떤 기능이 필요한지 정리해요.
4. 요구사항 정리하기
    - 개발자와 디자이너가 이해할 수 있도록 기능을 문서화해요.
    - 기능 명세서, 와이어프레임이 해당 문서의 예시입니다!
5.  디자인/개발 팀과 소통하기
    - 기획 의도를 설명하고, 팀원들이 기능에 대해 동일한 판단을 할 수 있도록 도와줘요.
6. 우선순위 조율하기
    - 시간, 자원의 제약에 따라 가능한 범위를 조율하기도 해요!
7. 결과물 검토하기
    - 개발된 기능이 원래 기획 의도대로 동작하는지 확인해요.

모든 결정을 혼자 내릴 필요는 없어요! 다른 팀원들과 소통을 해보아도 좋고, 기존부원 분들께 자문을 구해도 괜찮답니다😊

+) 기획팀에서 스쿼드의 리드를 맡는 경우가 많아요!

리드는 스쿼드가 목표를 잃지 않고 끝까지 결과물을 만들 수 있도록 방향을 잡고, 사람들을 조율하는 역할을 합니다.

리드의 역할에 대해서도 간단히 소개할게요!

1. 팀 빌딩
   - 한 학기 동안 함께할 팀이니 친밀한 관계를 유지하는 편이 협업하기 좋겠죠?
   - 자기소개, 스몰토크, 회식
2. OKR 설정
   - 스쿼드가 무엇을 만들고 있는지, 왜 만들고 있는지 계속 확인할 수 있도록 OKR을 설정해요.
3. 일정 및 진행상황 관리
   - 회의 일정을 잡고, 진행 상황을 체크하며 진행 흐름을 관리해요.
   - 회의는 오프라인을 권장합니다!
   - 우선순위 조정, 지연 작업 확인
4. 회고하기
   - KPT는 프로젝트나 업무를 돌아보고 발전시키기 위해 사용하는 가장 직관적이고 효과적인 회고 방법론이에요!
   - [KPT 회고](https://brunch.co.kr/@fall-spring/8) 👉 KPT에 대해 설명해놓은 글이에요.
